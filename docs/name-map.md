# CLI ↔ MCP name map

Every tool is defined once and exposed twice: as a `rollout` subcommand and as
an MCP tool. Same handler, same arguments, same result.

| | CLI | MCP |
| --- | --- | --- |
| Namespace | `rollout play …` | `play_…` |
| Grouping | by noun (`rollout play release halt`) | by verb (`play_halt_release`) |

The two front-ends order words differently on purpose. On the CLI,
`rollout play release --help` should show everything you can do to a release.
Over MCP an agent scans a flat list of tool names, where `play_halt_release`
reads as an action while a noun-first spelling reads as a namespace.

Because the mapping is not mechanical, every command **declares** the MCP tool
it shares a handler with (`Annotations: mcpTool("halt_release")`), and
`TestCLIAndMCPSurfacesMatch` fails the build when the two sets disagree.

## Rules

- **Tool names are written unprefixed at the registration site.** The registrar
  (`toolRegistrar` in `mcp.go`) applies `play_`. Never hand-write the prefix —
  it would double up.
- **Every tool is registered in two places**: the platform's `Commands` in
  `platform_play.go` (CLI) and `registerPlayTools` in `mcp_play.go` (MCP).
- **Shared commands are not namespaced** and are CLI-only: `login`, `doctor`,
  `config`, `confirm`, `audit`, `mcp`, `version`. An MCP host has its own
  configuration and its own confirmation UI; exposing `rollout login` as a tool
  would let an agent rewrite the user's credentials.
- **Arguments match too.** A CLI flag `--package` is the `package_name` field of
  the MCP tool's input schema, generated by reflection from the same `Args`
  struct. Kebab-case flags become snake_case fields.

## Monetization

| CLI | MCP |
| --- | --- |
| `rollout play products` | `play_products` |
| `rollout play product set` | `play_update_product` |
| `rollout play subscriptions` | `play_subscriptions` |
| `rollout play subscription get` | `play_subscription` |
| `rollout play subscription base-plan set-state` | `play_set_base_plan_state` |
| `rollout play subscription offer set-state` | `play_set_offer_state` |

The state changes are the one place the noun-first / verb-first split does more
than reorder words. On the CLI `activate` and `deactivate` would read as two
verbs; over MCP they are one operation with two values, and a tool is registered
once under one name. So the state is an argument — `--state active|inactive` —
rather than two commands that would both claim `play_set_base_plan_state`.

## Confirming a write from either front-end

A write tool returns a preview and a confirm token on its first call. Apply it
with `--confirm <token>` on the CLI, the `confirm` argument over MCP, or
`rollout confirm <token>` from anywhere — the staged record names the platform
that created it, so the token routes itself.
